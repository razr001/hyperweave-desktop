# HyperWeave Desktop mode

Business plugins are deferred by the user as of 2026-11-04, pending a possible architecture change. Existing plugin interfaces are retained, but live plugin publication/execution/revocation is not an accepted feature of this delivery. No Kata setup is needed for the current desktop acceptance scope.

The root `start` / `dev` commands and workspace `start:hyperweave` entry is a standalone HyperWeave workbench rendered from local bundled assets. It does not load or wrap the platform console, and it does not import or start the DSH `NextDesktopRuntime`, Host process, Harness profile, or plugin loader. A sandboxed Electron window exposes a narrow IPC bridge; the main process sends authenticated requests only to the administrator-configured HyperWeave origin and denies external navigation and renderer network access.

Configure the platform URL with `HYPERWEAVE_PLATFORM_URL` or create `hyperweave-desktop.json` in Electron's `userData` directory:

```json
{ "platformUrl": "https://hyperweave.example.internal" }
```

Only HTTPS is accepted except for loopback development addresses. API, role Agent profiles, Skills, plugins, knowledge bases, task events, approvals, and artifacts all come from this origin. Email/password login and refresh tokens are handled by the main process; refresh tokens are encrypted with Electron `safeStorage` when the OS provides it. The desktop configuration contains only the platform URL.

Persisted sessions are bound to the configured platform origin. Changing that origin requires a new login; older session files without an origin binding are also ignored. Concurrent API and download requests share one token refresh. A temporary refresh failure keeps the session for retry, while an invalid refresh token clears it. A late refresh response cannot restore a session after logout.

The upload picker accepts the platform's supported formats: PDF, DOCX, PPTX, XLSX, PNG and JPEG, up to 100 MB per file. Other extensions are rejected before creating remote documents.

The workbench reads `/api/skills/catalog`, which returns only enabled, published Skills allowed for the authenticated tenant role. Plugin choices come from `/api/agent/plugins/catalog`. The platform validates every new role binding against these eligibility rules; execution still checks current permissions and revocation. Retained unavailable bindings are displayed in the editor so users can remove them without losing the rest of their role configuration.

Tenant administrators can open pending tasks from the approval queue. The approval card shows the Skill, capability, risk level and exact invocation input. Approval stays disabled if those details cannot be loaded or the current administrator requested the invocation. The server makes the final authorization decision. Task titles use the platform's persisted original user request; role and runtime instructions remain in the execution prompt.

When an active task cannot be synchronized, the workbench keeps its last complete task state, events and artifacts and shows a synchronization notice. Polling resumes reading the existing task after connectivity returns; it does not submit another task or invoke execution recovery. `OUTCOME_UNKNOWN` still requires the explicit platform recovery action. The Electron smoke verifies a failed event request, preserved history and automatic read-only reconnection.

For opt-in acceptance against a real local platform, run `node dsh-desktop-next/scripts/verify-hyperweave-live.mjs` from the repository root after building. Set `HYPERWEAVE_TEST_CREDENTIALS` to the protected acceptance JSON file containing `userEmail` and `userPassword`, and `HYPERWEAVE_TEST_PDF` to a synthetic PDF. Its expected project code defaults to `ORCHID-739` and can be changed with `HYPERWEAVE_TEST_EXPECTED`. Set `HYPERWEAVE_PLATFORM_URL` for a loopback deployment and optionally `HYPERWEAVE_TEST_EVIDENCE` for screenshots and the result report. This creates a role, knowledge base, document and sandbox task in the test tenant. It verifies real Electron login, role persistence after reload, upload/indexing, scoped execution, cited result rendering and saving the result. It leaves remote test records for inspection and removes its temporary local session.

Optionally set `HYPERWEAVE_TEST_SKILL_ID` to an approved, published test Skill with the `knowledge.search` capability to exercise desktop binding and request retrieval through that Skill. For the interactive flow, set `HYPERWEAVE_TEST_INTERACTIVE=1`, supply a HIGH-risk (approval-requiring) read-only knowledge Skill, and include `adminEmail` and `adminPassword` for a different tenant administrator in the credential file. This additionally verifies task input through the desktop, discovery and approval in a separate administrator desktop session, resumed execution, and downloading a published text artifact. It never injects task states or disables platform safety checks. These flows do not verify plugin publication or revocation; use platform audit records to confirm individual capability execution.

Set `HYPERWEAVE_TEST_ARTIFACT=1` to exercise text artifact publication and download without requiring a Skill or approval. This requires a platform that supports readable `content` in `publish_task_artifact`. The platform performs UTF-8 encoding and screens the complete file before storing it; the model does not need to construct Base64. Live failures write `failure.json` and a screenshot, and do not count as passing evidence.

Run `node dsh-desktop-next/scripts/verify-hyperweave-catalog.mjs` with the same protected credential file and a loopback platform to verify real catalog and binding authorization. It creates synthetic Skills, has a separate administrator review and publish them, checks role filtering and rejected bindings, disables the published fixtures, and verifies removal of a retained binding. It leaves test records and writes a credential-free evidence report. This checks rejection of an unknown plugin ID; it does not claim to publish or execute a real plugin.

For development, use root `yarn start` (or `yarn dev`), which builds the dedicated HyperWeave main process and UI before launching. Root `yarn build` builds only those assets; `yarn check` runs typechecking, focused client tests and the build without launching a window. Use `yarn dist` and `yarn verify:package` to build and inspect the current-platform distribution. Historical DSH commands require explicit upstream maintenance commands and are not part of this path. The local workbench supports platform sign-in, role Agent profiles, approved capability bindings, local file uploads to selected knowledge bases, scoped task submission, task progress, approvals, follow-up input, results, and artifact downloads. Run `yarn workspace dsh-desktop-next verify:hyperweave-network` to launch the actual Electron app against local test servers and verify login, authenticated task submission, allowed platform API access, external request blocking, navigation blocking, and popup denial. To package the HyperWeave-only application, run `yarn workspace dsh-desktop-next dist:hyperweave`, then verify it with `yarn workspace dsh-desktop-next verify:hyperweave-package`. The app version defaults to `0.1.0`; release automation can set `HYPERWEAVE_DESKTOP_VERSION` to a valid semantic version. Packaging uses an isolated project directory with only the HyperWeave entry, preload bridge, local UI assets, product metadata, platform icons, and required licenses; DSH Harness runtime dependencies are not copied into the app.
